# 滚动计划 · 从声明到能跑

- **日期**：2026-10-20
- **状态**：M0 / M0.5 / M1 / M2 / M3 已完成（均经真事件验收）；M4 审计侧已落地（P-12 路由真源、P-13 findings 执行层、P-14 真跑与红绿证据均完成），**P-14 收口为手动触发、不挂 required**（理由见 `p14-audit-manual-gate.md`）；L4 接入层按计划延后

## 背景

声明侧已齐：状态机、判定器、事件归一、唯一写者 workflow、四份契约文档，`npm run check` 绿（配置自洽 + lint + 23 测试）。
但 `npm run check` 只证明**声明自洽**，证明不了**链路能跑**：没有远端、没有 `state:*` label、没有 required check，唯一写者从未在真实事件上执行过一次。

当前没有真实平台实例。所以「审计两执行器 / findings schema / 模型路由」这类最贵的环节现在做出来，只能拿编造数据自证——那种绿比红灯更坏，延后。

## 决策

按**能不能在真实事件上被验证**排序，分 4 个里程碑、10 份提案。每一阶的完成判据必须是「一条能当场跑出来的命令」或「一次能看见的 label 变化」，不接受「写完了」。

层级 → 里程碑对应：

| 层 | 是什么 | 里程碑 |
| --- | --- | --- |
| L0 | 声明（状态机、策略、契约） | M0 |
| L1 | 机制（判定器、事件归一、唯一写者） | M0–M1 |
| L2 | 门与门牌（能不能合由机械判定） | M2 |
| L3 | 派生物（知识库汇入） | M3 |
| L-UI | 平台（web 视图 + 命令入口，无自有状态） | M0.5 |
| L5 | 审计 | M4 |
| L4 | 接入层（飞书/钉钉/CLI） | 延后 |

## M0 · 自举：让第一条需求真的被自动受理

目标：一条真 issue 从无状态到 `state:accepted`，label 由 CI 自动加，全程零人工。

- P-01 默认流程：proposed 自动受理（声明侧）· **已完成**
- P-02 写者按策略落状态（机制侧）· **已完成**
- P-03 远端与仓库设置 + 首个真实事件验收（人工主导）· **已完成**

完成判据：`gh issue view <n> --json labels` 显示 `state:accepted`，且创建与落状态之间没有任何人点过 label。

**判据已达成（2026-10-21）**：issue #1 创建后 label 由 `github-actions[bot]` 自动加上，时间线无人工操作，run 39533142226 绿。

## M0.5 · 平台：一个能看见、能操作的本地 web

目标：把声明与账本折叠成一个页面，写操作全部经同一个判定器。

- P-11 平台形态：单进程 JavaScript，不做前后端分离

完成判据：`node scripts/server.mjs` 起得来，页面完成一次「提需求 → 看板出现 → 裁决 → 状态变化」，且判定器拒绝时账本行数不变。
顺序理由：远端不可用时，本地账本是唯一能让链路真跑起来的数据源；P-03（远端）降级为可选分支。

## M1 · 写者闭环：PR 事件也自动推导

目标：开发阶段的状态流转不再依赖谁记得去改 label。

- P-04 PR 事件推导 `accepted → in-progress`、`blocked → in-progress`
- P-05 拒绝与 INFRA 留痕（退出码三分，不静默当通过）
- P-06 验证脚本自己的反向用例（假绿灯是这里唯一的真风险）

完成判据：开一条真 PR 关联 accepted issue，issue 自动进 `in-progress`；构造一次非法转换，issue 收到拒绝评论且 job 留痕。

## M2 · 门：能不能合由机械判定

目标：`done` 不由评论、不由人眼看，由 required status check 判定。

- P-07 门牌幂等重算 · **已完成**（重算脚本 + workflow + 11 用例；真 PR 上的重算待第二个 PR）
- P-08 merge gate 四条守卫 · **已完成**
- P-09 挂成 required check + 分支保护 + 禁直推 · **已完成**（ruleset main-guard）

顺序理由：守卫第 4 条是「门牌必须含本 PR 编号」，门牌不能先算出来，门就无从判。所以 P-07 必须先于 P-08。
完成判据：故意破坏任意一条守卫，GitHub 真的拦住合并（截图为证），而不是「workflow 打印了 FAIL」。

## M3 · 派生物：知识库汇入

- P-10 知识库汇入（失败不阻断合并，按 path + sha256 幂等）· **清单侧已完成**（真实知识库本体尚未存在）

完成判据：同一次合并触发两次汇入，两次结果一致且不产生重复记录。

## M4 · 审计：拿真 findings 才判

目标：AI 产出的改动有没有被真跑过审查，由 Check Run 判定而不是由一句「我审过了」。

- P-12 路由真源（逻辑名 → 模型只在 `routing.yml`）· **已完成**（note 已进 implemented/）
- P-13 findings 契约执行层（schema + verdict 归一 + 双执行器比对 + Check Run 回写）· **执行层已完成**；`conclusion: neutral` 的假设已被证伪并改用 `action_required`
- P-14 把 `audit` 真跑一轮并挂成 required check · 待上游执行器（网关 + 沙盒）产出真 findings

为什么现在做：审计此前延后的理由正是「没有真 PR 与真门时只能拿编造数据自证」。真 PR #2 / #4 / #6 跑过门之后，这个理由不再成立。
顺序理由：先有「逻辑名怎么映射到模型」的真源，判据才不会被写进两处；先有 findings 的 schema 与归一，Check Run 才有东西可写。

完成判据：用真 PR 的 diff 产出一份 findings，`audit` 这个 Check 在 PR 上真的报红/报绿；把某个执行器改成 INFRA，门仍然放行但留痕里能查到这次 INFRA。

## 仍在延后的一件事

- **接入层（L4）**：当前需求由人直接在仓库里提，没有任何外部系统在发命令。接入层只发命令不写状态，晚接不影响任何不变式。
