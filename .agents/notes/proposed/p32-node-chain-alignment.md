# P-32 需求对齐：链条 · 节点 · 状态转换

- **日期**：2026-10-27
- **状态**：proposed（需求已对齐到可收尾；未进入方案设计）
- **一句话**：让「一条需求在一条既定链条上从评估走到上线」成为平台自己的一等对象，不再借 GitHub 的 PR 门与 required check 表达推进。

## 一、这份文档的边界

只记「要什么」与「不要什么」。不记数据表、不记接口路径、不记模块划分——那些等 §十 的假设被推翻或确认后另开一份方案记录。

## 二、名词

| 名词     | 指什么                                                                         |
| -------- | ------------------------------------------------------------------------------ |
| project  | 一个代码仓库 + 若干条链条 + 若干条需求                                         |
| 链条     | 一份 project 上的有序节点序列，如 fixbug 链、需求链                            |
| 节点     | **封闭的六类之一**（见 §四），用户不可新增类型                                 |
| 节点实例 | 某条需求站在某个节点上的那一份：状态、评论区、产物、已执行轮次                 |
| 需求     | 从接入层进来的一件待办：文本 + 可选图；fix bug 与新需求同等对待                |
| 当前位置 | 这条需求当前落在哪个节点实例上——由各节点自身的状态决定，没有单独一张「进度表」 |

## 三、已固定的裁决

| #   | 裁决               | 含义                                                                                       |
| --- | ------------------ | ------------------------------------------------------------------------------------------ |
| 1   | 没有独立编排器     | 节点自己就是链条的一部分：每个节点自带评论区与状态转换器，「需求走到哪」由节点上的状态表达 |
| 2   | 一个节点只干一种活 | 「接受节点」被删掉，它那点活并进需求评估节点                                               |
| 3   | 每个节点带审核     | 每个节点声明审核方：AI 审核 / 人审核（取代原先「推进权一律归人」）                         |
| 4   | 仓库在外部         | 代码仓库在 GitHub / GitLab；不用 Actions、不用 required check、不用 PR 门做推进条件        |
| 5   | 节点类型封闭       | 六类写死，用户只能编排顺序，不能自定义节点类型                                             |
| 6   | 链条首尾固定       | 需求评估是头，上线是尾；中间任意编排                                                       |
| 7   | 评论就是评论       | 评论是记录，不作为下一节点的输入                                                           |
| 8   | 追加规则是节点级   | 重跑前可往该节点的 `AGENTS.md` 追加规则，默认文件不动                                      |
| 9   | 合并不由平台执行   | 人在 GitHub / GitLab 上合；平台不碰仓库写操作，怕 agent 弄坏主线                           |

## 四、节点六类

| 节点     | 执行者 | 注入                                             | 产出                                     | 审核    |
| -------- | ------ | ------------------------------------------------ | ---------------------------------------- | ------- |
| 创建     | 容器   | docker 模板 + `BASE_URL` + `model` + `AGENTS.md` | 脚手架 / 初始化（project 级，见 §十 P1） | AI / 人 |
| 需求评估 | 容器   | 评估 `AGENTS.md`                                 | 可能增删改设计文件、产生 TODO LIST、评论 | AI / 人 |
| 开发     | 人     | —                                                | 在分支上开发；人按提交                   | 人      |
| 交叉测试 | 容器   | 测试 `AGENTS.md`                                 | 一条评论                                 | AI / 人 |
| 合并     | 人     | —                                                | 人在 GitHub / GitLab 上把分支合回主线    | AI / 人 |
| 上线     | 容器   | 上线 `AGENTS.md`                                 | 成果 + 评论                              | AI / 人 |

容器模板默认三种：deepseek harness / codex / claude，可新增。容器节点的共同契约：注入 `BASE_URL`、`model`、`key` 与该节点配置的 `AGENTS.md`，跑完把成果写进该节点评论区；**不修改默认 `AGENTS.md` 文件**。

## 五、链条规则

- 一条 project 可建 N 条链条，按类型区分（fixbug 链、需求链…）
- 每条链是六类的有序子集；约束：头 = 需求评估，尾 = 上线，节点不重复
- 链条上已有需求在走时改定义，只影响之后新进来的需求

## 六、分支

进链即建分支：需求一进入链条就产生一条分支，此后所有更新——设计的、代码的、测试文件的——都发生在这条分支上。没有接受节点，那条「当前 TODO LIST」的 commit 由需求评估节点产出。

## 七、状态转换

- 每个节点都可评论，人也一样；评论是记录，不往下游传
- 审核通过 = 提交 → 落到下一节点的待办；审核不通过 = 拒绝 → 回滚到上一节点
- 没有上一节点时被拒 = 整条需求被拒，经接入层回告提需求的人
- 每个节点都可重新执行；重跑前可往该节点的 `AGENTS.md` 追加规则（节点级），默认文件不动

## 八、接入层

- 需求接口：project key + context（文本，有时带图）
- create project
- project list

## 九、非目标

- 不用 GitHub Actions 做推进
- 不用 required status check 当合并条件
- 不用 PR 门表达「能不能进下一步」
- 不由平台执行合并
- 不允许用户自定义节点类型

## 十、收口假设（逻辑推出来的唯一解，可推翻）

以下五处原先是待定项。按你已固定的几条往下推，每处只剩一个自洽答案；记在这里当假设，**推翻任何一条都会改动状态机本身**。

| #   | 假设                                                                               | 为什么它只剩这个解                                                              |
| --- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| P1  | 创建节点是 **project 级的一次性动作**，不在链条里                                  | 链条头已被定成需求评估；创建若也在链内就会出现两个头                            |
| P2  | 审核方是 AI 时，容器跑完自审、通过即推进；审核方是人时，等人按                     | 「每个节点带审核」若不能推进就等于没有审核，而人审核节点（开发/合并）本来就等人 |
| P3  | AI 审核由 **该节点自己的容器在同一次执行内完成**，不另起执行体                     | 「一个节点只干一种活」＋不新增执行体；另起审核体是新的自由度                    |
| P4  | 需求评估只能改 **设计与计划类文件**（设计稿、TODO LIST），不许改代码 / 测试 / 配置 | 它被允许「增删改设计文件」，边界若不写在节点上，等于给了一个能改全仓的容器      |
| P5  | 合并完成的认定 = **人按提交**，平台不去核对主线里是否真有这些提交                  | 平台不碰仓库写操作；真去核对就得读远端状态，等于把判定依赖到外部仓库的即时状态  |

P2 与 P4 是这五条里唯一两处会改变「谁在什么时候可以推进」的，若与你的想法不同，先改这两条。
