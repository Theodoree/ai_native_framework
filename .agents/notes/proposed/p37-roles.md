# 角色：权力挂在节点上，身份用口令承载

状态：implemented（2026-10-27，t33 已实现并通过黑盒复验）
相关模块：`apps/chain`（model / store / http）

## 需求原话

> 帮我做一个角色 API：创建角色，角色会归属于某个 project，角色会有审核、开发、测试等权力，其实就是配节点的权力，评论权都是大家都有，这里是确认和拒绝的权力。

## 平台现在缺什么

平台此前**没有任何人员身份**：只有 project 级的 intake 口令（谁拿这个口令谁就是这个 project 的接入方）。节点上的"接受/拒绝"是人按的，但服务端分不清按的人有没有资格。这一层就是要把"能不能按"从"知道接口地址"变成"持有对应权力"。

## 决定了什么

1. **身份用口令承载，不做账号体系**。建角色时平台发一个 `roleToken`，请求带 `Authorization: Bearer <roleToken>` 就代表这个角色在操作。
   - 放弃：账号 + 密码 + 会话。这一轮要的是"权力从无到有"，账号体系会引入密码存储、会话过期、找回流程，都是与本轮目标无关的工程量。
   - 放弃：只记人名不做校验。那样"权力"只是字面意思，任何知道接口的人都能按。
   - 迁移路径：token → 角色的解析集中在一处，将来换真账号只改那一层。
2. **权力是四个枚举值**：`review`（审核）/ `dev`（开发）/ `test`（测试）/ `release`（上线）。
3. **权力挂在节点上，按节点类型默认对应**：`assess→review`、`dev→dev`、`crosstest→test`、`merge→review`、`release→release`；建链时**可以**逐站覆盖（同一类型在不同链上分工可能不同）。
   - 放弃：完全由建链时指定。每个节点都必须配，漏配一次就变成"谁也按不了"，而漏配不会报错。
4. **默认拒绝**：`accept` / `reject` / `run` 都必须带某个对**这个节点**有对应权力的角色口令，否则 403 并点名缺哪个权力。没有配置任何角色的项目，人只能看，不能按。
   - 理由与仓库其它判据一致：判不了当拒绝。宽松模式的坏处是"没配角色"会变成常态。
   - 代价：建完项目必须建角色，否则按钮点不动。缓解办法是建项目时可选自动生成一个 `owner` 角色（拥有全部四个权力），首轮先不做自动生成，靠文档与 403 文案指路。
5. **评论不校验权力**：谁都能评论；带了有效角色口令就把作者记成那个角色（`authorType=role`），没带就记 `visitor`。
6. **创建/列出/删除角色需要 project 管理口令**（`-admin-token`，与建 project 同一把），不是角色权力——否则任何一个有权力的人都能给自己发新角色。

## 数据形状

```
roles(id TEXT PK, project_key TEXT, name TEXT, powers TEXT /* JSON string[] */, token TEXT UNIQUE, created_at TEXT)
```

- 角色属于 project（`project_key`），删 project 不影响既有角色只影响可达性（本轮不级联删）。
- `token` 只在创建与轮换的响应里出现一次，列表接口不回显。

## 接口

| 方法 | 路径 | 认证 | 说明 |
| --- | --- | --- | --- |
| POST | `/api/p/{project}/roles` | 管理口令 | 建角色，201 返回角色与 `token`（仅此一次） |
| GET | `/api/p/{project}/roles` | 管理口令 | 列出角色，不含 token |
| POST | `/api/p/{project}/roles/{id}/rotate` | 管理口令 | 换口令，旧口令立即失效 |
| DELETE | `/api/p/{project}/roles/{id}` | 管理口令 | 删角色 |
| — | 既有 `nodes/{node}/{run,accept,reject}` | 角色口令 + power | 403 文案点名缺哪个权力 |
| — | 既有 `nodes/{node}/comment` | 可无 | 带有效口令则记作者角色 |

## 判据（实现时必须有）

1. 没有角色口令按 accept → 403，且文案指出"需要一个带 <power> 权力的角色"。
2. 有角色口令但权力不对 → 403，文案点名角色与缺少的权力。
3. 权力对的角色 → 200，且在节点评论里记下是谁按的。
4. 评论不校验权力：无口令 200、有口令 200 且作者是角色。
5. 角色口令不能跨 project 使用（别的 project 的角色 403）。
6. 换口令后旧口令立即 403。
7. 列表接口不回显 token。

## 已知边界

- 口令无过期、无审计（谁在什么时候用哪个口令做了什么，只有节点评论这一条痕迹）。
- 一个请求只能是一个角色，没有"多角色合并"。
- 没有角色 → 项目所有人按不动，首次配置靠 403 文案指路。
## 落地记录（t33，2026-10-27）

**代码落点**：`apps/chain/roles.go`（新建：四种管理动作 + `roleFrom` 唯一解析点 + `requirePower` 闸门 + 三条 403 文案常量）、`model.go`（四权力常量、`defaultPower` 表、`PowerForNode`、`Role`/`HasPower`、`Node.Power`/`ChainNode.Power`）、`store.go`/`store_sqlite.go`（`roles` 表 + 五个存储方法 + `nodes.power` 列的 ALTER 迁移）。

**进链时把权力定死**：`NewRequirement` 就把每站的 power 写进快照，之后链条改版不影响已在飞的需求。

**黑盒复验（我自己跑，不是自述）**：起真服务 `-admin-token admin1`，逐条探：

| 动作 | 结果 |
| --- | --- |
| 无口令 run | 403 `这个动作需要一个带 review 权力的角色口令` |
| 只 `test` 权力的角色 run assess | 403 `角色「测试员」没有 review 权力，不能在这个节点上确认/拒绝` |
| `review` 权力角色 run/accept assess | 200，评论作者 `role/审核员`、verdict `approve` |
| 拿 beta 的角色操作 alpha 的需求 | 403 `角色属于 beta，这条需求在 alpha` |
| 列角色 | 200，响应体**不含** `rl_` |
| 换口令 | 旧口令 403（不再被认作任何角色），新口令过闸门（落到 409 状态冲突，说明权力已通过） |
| 匿名评论 / 角色评论 | 200 `visitor/visitor` / 200 `role/测试员2` |
| 非法权力值 | 400 `不认识的权力：bogus（只能是 review / dev / test / release）` |

**已知代价（未解）**：不给 `-admin-token` 的部署里，角色管理接口返 503，于是建不出角色 → 所有动作 403，整条链按不动。这是"建角色必须用管理口令"的直接后果，处置见下一节。

## 待办：没有管理口令时的引导

单机跑起来（`-exec fake` 什么都不配）是最常见的第一次体验，不能让它卡在"建不出角色"。方案：建 project 的响应里带回一个 `owner` 角色口令（四个权力全给），只显示这一次。

理由是它与现有的信任模型一致：`POST /api/projects` 本来就不需要认证，谁能建项目谁就拿到这个项目的钥匙。**不**放宽"角色管理需要管理口令"，否则那一条就成了摆设。
