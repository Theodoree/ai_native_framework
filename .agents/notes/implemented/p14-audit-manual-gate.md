# P-14 收口：审计判定保持手动触发，不挂 required

- **日期**：2026-10-26
- **状态**：已落地（决策：人）
- **相关**：`docs/workflow.md` 的「审计判定：手动触发是当前形态」；PR #14（受信 ref 执行面）挂着未合

## 选了什么

审计判定（两份审查结论进同一套口径，出「通过 / 要改 / 驳回 / 判不了」）**保持手动触发，不挂 required**。合并前的动作是：维护者显式触发一次，把两份结论作为参数喂进去，看它落哪一档。

## 为什么

1. **输入不是机器能生成的**。这道判定的输入是人对这次改动的判断。自动触发（`pull_request_target`）拿不到结论，只能落「判不了」。
2. **「判不了」按本仓口径不允许合并**（决策 B：未判过等于没审过，见 `AGENTS.md` 安全红线第 4 条）。两条合起来，自动挂 required = 每个 PR 自己把自己锁死。
3. **永远红的检查会被当噪音忽略**。一道从不通过、也没有人能修它的闸门，训练出来的行为是绕过它，而不是改进它。

## 代价（写在明处）

「合并前跑过一次审计」靠流程清单和人的自觉，不靠机器拦。机器拦不住的东西，也不能在报告里说成「已由门保证」。

## 什么会推翻这个决定

不是「判据不够多」，而是「结论从哪来」这一半：当审查结论能作为**受信产物**出现（例如由人在基分支上提交一份结论文件，工作流从基分支读它），自动触发就有了真实输入，那时才谈得上挂 required。另外两条已登记的前置仍成立：

- 自证是快照：回读之后写入的同名结论会盖掉真结论，需要时序判据或 nonce；
- 同名 check 的归属：任何能发 Check Run 的工作流都能发一条 name=audit 的 success。

这两条不解决，「挂 required」只是把门槛抬到自己人也过不去的高度。

## 放弃的选项

- **B findings 入库 + 自动触发 + 挂 required**：门真正自动化，但要新增一条「谁有权提交 findings」的规矩，以及每次审查多一次提交。当前收益不抵这部分复杂度。
- **分两档挂 required（只判「有没有人给过判定」）**：本质上还是手动，只是把「人有没有做」换成一条更难解释的检查。

## 留下的东西

PR #14（audit 受信 ref 执行面：从基分支 checkout、trusted 输出、闸门）**保持开启不合并**——它的改造本身成立（被审对象不该决定用哪份脚本执行审查），缺的是「输入从哪来」这一半；等结论入库那条路被决定时，它是现成的前半段。
