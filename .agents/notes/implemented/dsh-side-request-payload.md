# DSH 运行时：压缩只改「模型看得见的请求」，side request 读的是原始日志

- **日期**：2026-10-27
- **状态**：implemented

## 现象

同一天里两次，整个会话被同一堵墙拦住：

```text
413 side_request_payload_too_large
```

拦住时的表征很反直觉——**模型自己的上下文一直很稳（约 160K），可一旦撞上，所有工具调用都失败**，包括 `compress`。也就是说，连「压缩」这个本该用来救场的工具都被同一堵墙拦在外面，会话无法自救，只能开新会话。

当时的量级：side request 载荷从 4.8M 涨到 **5.24M**，而审查模型窗口只有 **1M**。

## 机制

两件互不相干的事被误当成一件：

**① billion-context 是「改写请求」的代理，不是「改写日志」的工具。** 它在请求发出前把已消化的区间换成摘要、保留最近若干条原文；原始内容只留在本地，靠 `decompress` / `search_context` 才读回来。它管的是「模型这一次看得见什么」，**不管「会话日志里存了什么」**——日志一条不少，工具输出原样在内。

**② DSH 的工具调用前置审查（auto review）是另一个请求。** 它必须在工具真正执行之**前**发生，因此等不到「压缩后的视图」——那一刻还没有要发送的请求。它取的是**未压缩的原始会话**。DSH 分发实现的注释把这件事写得很直白（`dsh-ptc-runtime-node` 的 `process.js`，`approval policy=ask` 时该路径生效）：

> side requests bypass compression by design #388

于是两条曲线走向相反：被压缩的那条持平在 160K，绕过压缩的那条随工具输出**单调增长**。谁先撞窗口，取决于会话里堆了多少工具输出——通常是 side request 先撞，而且撞的时候模型侧一点征兆都没有。

## 为什么会反复咬人

- **报错信息只报「side request 太大」，不告诉你「压缩管不到它」**。第一反应必然是「那我压缩一下」——而 `compress` 本身要经过同一道审查，于是也被拦。诊断回路在这里闭合不了，只能靠先验知识跳出去。
- **模型侧看不到任何异常**。上下文占用、压缩命中率、摘要质量全都正常；判断「快撞墙了」的唯一信号是工具输出体量本身，而它恰恰是最容易被忽视的。
- **多 agent 会话天然喂大它**。子代理报告、`read` 大文件、`git diff` 全文、日志全文——每一样都是「一次性内容」，模型看完就扔，但它们全部沉淀在会话日志里，被 side request 一遍遍重读。
- **它是运行时属性，不是本仓的代码问题**。看仓库看不出来，只有在长会话里踩到才会发现，所以不落盘就会再踩一次。

## 应对

三道即时出口（择一，都需要人能改设置或换模型）：

1. **把审查模型换成窗口更大的**：1M 的审查模型对本仓的长会话偏小，4.8M 量级就已经超了。
2. **关掉 auto review**（或在不需要前置审查的探索阶段临时关）：代价是失去工具调用前的拦截，只在受控环境下用。
3. **开新会话**：唯一一定有效的手段——会话日志不继承，side request 从零开始。

工作习惯（治本，且不需要改任何设置）：

- **大文件只取需要的行区间**：`read` 带 `offset` / `limit`，不要整文件读；需要全貌时先 `grep` 定位再读窗口。
- **日志只取尾部**：`cmd > /tmp/x.log 2>&1; echo exit=$?` 之后读 `tail`，不要整份日志进上下文。
- **子代理报告要摘要，不要全文**：给子代理的交付要求里写清「报什么」，而不是让它把过程倒回来。
- **少用 `decompress`**：它把压缩掉的内容原样放回上下文，等于一次性把之前省下的全部还回去；真需要时用 `search_context` 定位再按块取。
- **长任务分段**：一个阶段性任务结束后开新会话接手，比在一个 5M 的会话里硬撑便宜得多。

## 证据与边界

- 两条数字来自本轮实测：模型上下文约 160K 稳定；side request 载荷 4.8M → 5.24M，审查模型窗口 1M，报 `413 side_request_payload_too_large`。
- 上游注释原文 `side requests bypass compression by design #388` 出自 DSH 分发实现 `dsh-ptc-runtime-node` 的 `process.js`；该文件在 DSH 应用包内，不在本仓，仓库内不可复现——这里记录的是排查结论，不是可重跑的用例。
- 本记录不含任何本仓代码改动：它是运行时事实与工作习惯的记录，因此落在 `implemented/` 而非 `proposed/`。
