# P-41 资格基线：项目是权限边界，建项目属管理员，提需求属成员

日期：2026-10-28　　状态：implemented

## 一、三条门，各自的理由

1. **建项目 = 管理员**。项目是权限的边界，而「往项目里加人」只有管理员能做。普通账号建出来的项目连他自己都进不去（`powersFor` 只认角色授予），那条路通向死胡同；而且开放建项目等于让任何登录的人往平台里灌命名空间。
2. **界面提需求 = 该项目成员**（管理员天生成员）。同一件事在接入层早就有这道门，界面侧却只查登录，于是「不认识的登录用户能往任何项目提需求」。两道门必须同口径，否则门只在后门那段上锁。
3. **建账号可带 `admin`**，仍只有管理员能调；**不做「把已有账号升级为管理员」**——升权是那种出事之后查不出来的操作，本期只支持建的时候决定。

顺序也有讲究：提需求先 404（有没有这个项目）再 403（你有没有资格），否则 403 会变成项目存在性的探针。这条有专门用例钉住。

## 二、一处措辞合并

成员资格这道门有三处用到（界面提需求、接入层提需求、接入层读结论），原来两处各写一句文案。收成 `denyNotMember` 一处，动词作参数（`提不了需求` / `看不到这条需求`）。理由：同一件事不该有两种说法，改文案时也只有一个地方要改。

## 三、判据与变异

`apps/chain/permissions_test.go` 4 条（建项目要管理员、成员才能提需求、顺序 401→404→403、建账号可指定 admin）。变异：删 `requireAdmin` → 红 2；成员判断恒真 → 红 2；忽略 `admin` → 红 1。真机 curl 亦验：普通账号建项目 403「只有管理员能做这件事」、非成员提需求 403「「lisi」不是 acme 的成员，提不了需求」、被授予 `dev` 后 201、`admin:true` 建出的号能建项目。

## 四、留下来的缺口（下一轮）

读的一侧还没上边界：`GET /api/projects`、`GET /api/requirements`、`GET /api/requirements/:id` 与图片三个接口仍只要求登录。于是任何登录用户都能看到所有项目的需求正文、图片与事件流——写的一侧有权力判定，读的一侧没有。这不是「以后再说」的洁癖：它让「项目」这个边界只挡住写，不挡住看。已派下一轮按同一口径补：列表只回自己参与的项目、需求详情与图片要求成员资格。
## 五、读的一侧补上边界（t56 落地）

原来写有权力判定、读没有：任何登录用户能读所有项目的需求正文、事件流与图片。补齐后：

- `GET /api/projects` 只回「我参与的项目」（管理员全部）；空列表返回 `[]` 不给 `null`——前端靠它区分「没有权限」和「一条都没有」。
- `GET /api/requirements` 只回「我有权的项目」下的需求。
- `GET /api/requirements/:id` 走成员门，顺序 401 → 404（没这条需求）→ 403（有但不是你的项目）。这条顺序是契约：403 排在前面就成了「这个 id 存不存在」的探针。
- 图片三个接口都走成员门：读用 `看不到这条需求`、传与删用 `改不了这条需求`。上传被拒时连上传目录都不会建，不留孤儿。

成员门收成一处 `requireMember(c, projectKey, action)`：先身分后资格，文案按动词参数化。同一件事只有一种说法。

变异六组各红一条（项目列表过滤、需求列表过滤、详情门、上传门、读图门、404 优先），真机 curl 另验：非成员的项目列表只剩自己那个、非成员读别人需求 403、读不存在的需求 404、非成员上传 403。

**仍未关的一条（下一轮）**：`nodeComment` 与 `nodeRule` 仍然只要求登录。这个洞比读更硬——非成员不仅能评论别人项目的需求，还能往那一站追加规则，而规则会被拼进容器的 `AGENTS.md`、在下一站被执行。也就是说，任何人可以把一句话塞进别人的 agent 上下文。
## 六、评论与追加规则的成员门（t57 落地，写侧最后一个洞）

`nodeComment` 与 `nodeRule` 原来只要求登录，任何账号能往别人项目的需求里写评论、更能往某一站追加规则。**规则比评论危险得多**：规则会被拼进容器注入的 `AGENTS.md`、在下一站真正执行——陌生人写的一句话就变成别人 agent 的指令。两条统一走 `requireMember`，文案分开（`评不了这条需求` / `改不了这一站的规则`），顺序仍是 401 → 404 → 403。

顺手清掉死代码：中间件 `apiNeedsLogin`（`accounts.go:219`）除 signup/login/bootstrap 之外全部要求登录，所以 `author, authorType := "visitor", "visitor"` 那条分支永远走不到。作者现在直接记 `user` + 账号名，`nil` 判断作为兜底保留——不假设中间件一定在。

真机验证：非成员评论别人需求 403、追加规则 403，读回该需求三个节点的 `comments=0 rules=0`（被挡下的一行都没落库）。变异：删评论门 → `TestCommentNeedsMembership` 红；删规则门 → `TestRuleNeedsMembership` 红；作者记回 `visitor` → 2 红（含一条既有用例）；404 改 403 → `TestCommentAndRuleAbsentBeatsForbidden` 红；规则门错挂评论文案 → 1 红。

至此写与读两侧的边界同口径：**能看见什么、能写什么，都由「你是不是这个项目的成员、你在这站有没有这个权力」决定**，没有第三套判断。
