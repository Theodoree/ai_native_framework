# 流程版 · 一次改动的顺序与判据

本文是流程版，规则真源是 `AGENTS.md`，本文只讲顺序与判据。

## 阶段：什么时候做 / 拿什么当证据

| 阶段 | 什么时候做 | 做完拿什么当证据 |
|---|---|---|
| 提需求 | 收到改动请求（人给的一句话、一个工单、自己发现的不对）后，写任何代码之前 | 目标句 + 一条可运行的验收命令 + 可动边界（可改的模块、不可碰的范围）；三缺一 ⇒ 不进下一段 |
| 拒绝 | 提需求之后、开发之前；开发中每次要动边界外的东西时重跑一次 | 命中时：停下点 + 已查到的证据 + 需要人拍板的一个二选一。未命中时无产出，直接进开发 |
| 开发 | 拒绝未命中 | 最小改动的差异 + 模块 README 状态标记（`active` / `stale` / `deprecated`）+ 决策 why 落在 `.agents/notes/` |
| 测试覆盖 | 实现落地后；缺陷修复要先有一个能复现失败的用例 | 测试用例（位置与断言强度按 `docs/testing.md`，命令按 `docs/development.md`）+ 验收命令的输出原文：逐项结果 + 结尾汇总行 |
| 测试脚本覆盖 | 本次改动动了验证脚本，或新增、修改了断言 | 每条新断言的反向用例：输入（去掉被保护的东西，或把期望值改错）+ 脚本报失败的输出 + 脚本汇总行的原文 |

## 拒绝：停下条件（命中任意一条即停）

规则依据在 `AGENTS.md` 的「安全红线」与「特性启用」；本表只写怎么判定命中、命中后做什么。

| 判定 | 命中后做什么 |
|---|---|
| 目标或验收判据本身要变（实现手段变不算） | 停下，回到提需求，让人重新确认判据 |
| 动作会写仓库状态：提交 / 打 tag / 推送 / 改历史 / 删分支 | 先问人，得到同意再做；不得先做后问 |
| 动作不可逆，或要动工作区之外的文件、别的目录、共享环境 | 停下，写清动什么、为什么必须动，等人确认 |
| 要新增依赖 / 服务 / 工具 | 停下，等人确认来源与许可证 |
| 需要凭据、密钥或更高权限，而手上没有 | 停下报告；凭据不得进仓库；疑似泄漏先停下上报，不自行改写历史 |
| 请求有两种合理解释，选错会改变对外行为 | 停下，给出两个解释 + 推荐答案，等人拍板 |
| 复现不出来，或证据不足，证明不了改动有效 | 停下报告现状与已试过的路径，不猜一个改动顶上 |
| 要改的范围超出提需求时写下的边界 | 停下，重新确认边界 |

反向判定：读文件、搜索、运行命令能查清的事实，自己去查，不拿去问人。

## 红线

- 不猜需求：三件套写不出可判定的一版，停，不写代码。
- 不越界：只改提需求阶段写下的边界内的东西。
- 不写仓库状态（提交 / 打 tag / 推送 / 改历史 / 删分支），除非人已同意，或项目已把这条开关改成允许（开关见 `AGENTS.md` 的「特性启用」）。
- 凭据不进仓库；发现疑似泄漏先停下上报。
- 不新增依赖而未获确认。
- 不把跳过、没跑、目视检查当成通过。
- 不声称完成而拿不出命令原文。
- 不偷偷改判据：目标和判据变了就回到提需求，不把判据改成好实现的那个。

## 验证结果的三种结局

| 结局 | 判定 | 对完成的影响 |
|---|---|---|
| 通过 | 命令返回成功，且该断言有反向用例证明它有判别力 | 计入已完成 |
| 失败 | 命令存在，但返回非零 | 阻断：不得进入收尾，不得声称完成 |
| 跳过 | 本机没有这个命令，或识别不到可执行的检查 | 不计入通过：补跑一次并贴出输出，或明确写下「未验证」 |

汇总行必须把三种计数分开；把跳过读成通过 = 把未验证写进结论。

## 反向用例（断言必须有判别力）

- 每条断言配一个反向用例：去掉被保护的东西、或把期望值改错，脚本必须报失败。
- 去掉保护后仍然通过 ⇒ 该断言没有判别力 ⇒ 按未覆盖处理，不得计入已验证。
- 能做成脚本内置的自检最好（一份必然命中的样本，证明检测器活着）；临时手工做也行，输入与输出必须进证据。

## 不算证据的说法

| 说法 | 换成什么 |
|---|---|
| 「已经理解了」 | 目标句 + 验收命令 + 边界 |
| 「改好了」「我跑过了」 | 命令输出原文：逐项结果 + 汇总行 |
| 「测试都过了」（只贴最后一行） | 逐项结果 + 三种计数分开的汇总行 |
| 「断言写好了」 | 反向用例的输入与输出 |
| 「应该没问题」 | 未验证就写未验证，并停下 |

> 这条链为什么这么设计（人读版）见 `docs/workflow.md`。
