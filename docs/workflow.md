# 一次改动怎么走完

一条改动请求从进来到交出证据，只走五段：提需求、拒绝、开发、测试覆盖、测试脚本覆盖。每一段的产出都必须是能当场判定的东西——一句写得清的目标、一条跑得起来的命令、一段贴得出来的输出。写不出可判定的东西，就说明这一段还没做完。

## 为什么是这条链

质量的定义是**可验证的行为符合预期**（理由见 `docs/principles.md`）。读代码只能得到「看起来对」，只有可重复运行的检查才能得到「确实对」：检查是主判据，人的 review 是补充。这条链就是把「一句话的请求」推到「一条可重复运行的检查」的最短路径——提需求把它写成判据，开发把它实现出来，测试覆盖把它钉住，测试脚本覆盖再确认钉住它的那套检查本身没坏。

链条上只有一类东西不归执行者：**决策**。目标、范围、风险、不可逆动作的取舍归人；事实（契约里写的是什么、这条命令能不能跑通、现状到底是什么）归执行者自己去查。这条线既决定什么时候该停下来问人，也决定什么时候不该问。

## 全貌

```text
需求进入
   |
   v
[提需求]        目标 / 验收判据 / 可动边界 全部写清
   |
   v
[拒绝]          命中停下条件?
   |---- 命中 ----> 停下问人（已查到的证据 + 需要人拍板的二选一）----> 回到 [拒绝]
   `---- 未命中
   |
   v
[开发]          读地图 -> 读模块契约 -> 最小改动 -> 写测试
   |
   v
[测试覆盖]      行为有测试 + 跑验证：失败阻断完成，跳过不等于通过
   |
   v
[测试脚本覆盖]  反向用例能抓住被去掉的保护
   |
   v
交付            命令原文 + 汇总行 + 状态标记 + 决策 why
```

## 提需求

进门的东西可能是一句话、一个工单，也可能是调试时发现的一处不对。这一段只做一件事：把请求变成**可判定的三件套**。

- 目标：什么行为要变成什么样；
- 验收判据：跑什么能证明它变了；
- 可动边界：可以改哪些模块，哪些不能碰。

三件套缺一件，就不进下一段。

为什么：写不出验收判据，通常不是因为懒得写，而是这件事本身还没被定义清楚；把它带进开发，代价是把不确定性固化成返工——代码写完才发现判据另有其解，或者要改的东西根本不在你以为的模块里。动边界之前先读两张地图：`docs/architecture.md` 给全局，目标模块的 `README.md` 给契约（做什么、不做什么、接口）；不读契约就动手，最常见的结局是把已有的能力重做一遍。

交出的东西：目标句 + 验收命令 + 边界。

## 拒绝：什么时候必须停下

分界线一句话：**事实归执行者，决策归人**。查得到的自己查（现状、契约、这条命令能不能跑通）；查不到、又必须由人承担的，停下来问。

以下每一条都能当场判定，命中任意一条就停：

- 目标或验收判据本身要变（实现手段变不算）；
- 动作会写仓库状态：提交、打 tag、推送、改历史、删分支；
- 动作不可逆，或要动工作区之外的东西：删除、覆盖、共享环境、别的目录；
- 要新增依赖、服务或工具；
- 需要凭据、密钥或更高权限，而手上没有；
- 请求有两种合理解释，选错会改变对外行为；
- 复现不出来，或证据不足，证明不了改动有效。

命中后交出的东西：停下点 + 已查到的证据 + 需要人拍板的一个二选一（可以带推荐答案，但不由执行者拍板）。

为什么：不可逆动作没有「回头改一版」这个选项——密钥进了提交历史，处理方式是轮换，不是删掉；目标和范围一变，原来的验收判据就作废，继续做只是把废弃的东西做厚；拿不准的解释猜一个再往下写，返工代价高于一句提问：反向的错同样犯不起——把本可自己查清的事实拿去问人，等于把该自己干的活推给人。

## 开发

把三件套变成最小改动：先读地图与模块契约，再动手。分支怎么拉、提交怎么写，按 `AGENTS.md` 的「工作流」与「工程规范」。

为什么：最小改动是「如无必要勿增实体」在流程上的形态——新增抽象、模块、配置之前先证明现有方案无法满足（理由见 `docs/principles.md`）；力气要花在热点上，在边角上打磨不会让整体变快。改完要留下痕迹：模块 README 的状态标记跟着代码走，决策的 why 写进 `.agents/notes/`——下一个接手的人或 agent 没有你的对话记忆，只能读记录。

交出的东西：最小改动的差异 + 状态标记 + 决策 why。

## 测试覆盖

改动带来的行为必须有测试把它钉住。测试写在哪、断言要强到什么程度，真源是 `docs/testing.md`；跑什么命令见 `docs/development.md`；收尾的验证闭环见 `.agents/skills/verify-change`。这一段在链条里的作用只有一个：把「实现做完了」变成「实现被钉住了」。

两条判据在写测试时就定下来：修缺陷先写一个能复现失败的用例（红），再让它变绿——红的那一次是这条修复存在的唯一证据；断言落在行为契约上，不落在实现细节上，否则下一次重构会把测试连同行为一起改掉，测试就不再是判据。

交出的东西：测试用例 + 验收命令的输出原文（逐项结果加结尾的汇总行）。

## 测试脚本覆盖

验证脚本自身也会坏，而它坏掉的方式是**静默通过**：断言写反、被保护的东西被删掉、路径改过，脚本照样打印一片通过。假绿灯比没有灯更危险，因为团队会按它下判断。

所以每条断言都要配一个**反向用例**：把被保护的东西故意去掉，或者把期望值改错，脚本必须报失败。去掉之后仍然通过，说明这条断言没有判别力——按未覆盖处理，不得计入「已验证」。反向用例做成脚本内置的自检最好（用一份必然命中的样本证明检测器活着），临时手工做也可以，但输入和输出要进证据。

同一段逻辑还要把三种结局分开：通过，是命令返回成功且这条断言有反向用例证明它有判别力；失败，是命令存在但返回非零，它阻断完成；跳过，是本机没有这个命令、或识别不到可执行的检查，它不是通过，只是没跑。三种结局分开计数、分开报告：把跳过读成通过，等于把「没验证」写进结论；发现某一项是跳过时，要么补上命令跑一次并把输出贴出来，要么明确写下「未验证」。

## 审计判定：手动触发是当前形态

合并前要有一道审计判定：两份独立审查结论进同一套口径，得出「通过 / 要改 / 驳回 / 判不了」四档之一。这道判定的输入不是机器自己生成得出来的——它是人对这次改动的判断，所以它现在只能由维护者在合并前**显式触发一次**，把两份结论作为参数喂进去。

为什么不做成自动触发的 required 检查：没有结论输入时，判定只能落成「判不了」，而「判不了」按本仓口径不允许合并（未判过等于没审过，见 `AGENTS.md` 安全红线第 4 条）。自动触发于是变成每个 PR 自己把自己锁死，而一道永远红的检查很快会被当成噪音忽略——被忽略的红灯比没有灯更糟。

所以当前的位置写在明处：审计判定**不挂 required**，而是「合并前的一个动作」。代价是「合并前跑过一次审计」靠流程清单和人的自觉，不靠机器拦。要把它变成机器拦，缺的不是更多判据，而是「审查结论从哪来」这一半——结论必须先作为受信产物出现（例如由人在基分支上提交），自动触发才有真实输入，才谈得上挂 required。

交出的东西：一次审计判定的结论原文——四档里的哪一档，以及两份结论的比对结果（一致几条、各自独有几条）。

## 交出证据

一次改动的完成判据是：适用的检查全部通过，并且证据能贴出来；没有通过的检查不算完成（见 `AGENTS.md` 的「准则」）。证据的最小集合：验收命令的输出原文、测试用例、模块 README 的状态标记、决策 why 的落点；改动碰过验证脚本或断言时，再加上反向用例的输入与输出。报告里要写清哪些项是跳过或未验证——绿灯只覆盖真正跑过并通过的那些。
